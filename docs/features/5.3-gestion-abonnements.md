# Feature 5.3 — Gestion des abonnements

## Statut d'implémentation
✅ **Implémenté sur les 3 couches.** Code : `lib/features/subscription/`
(entité `SubscriptionPlan`, enum `SubscriptionFeature`, repository, 7 use
cases, datasources Data, `SubscriptionBloc`, 4 écrans). Backend :
ressources `subscription.create-plan`, `subscription.update-plan`,
`subscription.delete-plan` sur la fonction Appwrite unique `api`
(Super Admin uniquement). Lecture/liste/recherche/temps réel en accès
direct client (`read(users)` sur chaque document - le catalogue n'est pas
sensible). Intégré au sidebar `AppShell` ("Abonnements", Super Admin
uniquement).

## Objectif métier
Les abonnements déterminent quelles fonctionnalités une entreprise cliente
peut utiliser. Gérés par le Super Admin uniquement — l'Admin entreprise
consulte son plan (visible en lecture seule dans `EditCompanyPage`/5.2)
sans pouvoir le modifier lui-même.

## Décisions de scope prises pendant la construction
- **Pas de statut actif/inactif sur un plan.** Le cahier des charges dit
  "CRUD" au sens littéral : supprimer un plan est une vraie suppression,
  pas une désactivation. Une entreprise encore assignée à un plan
  supprimé voit son `subscriptionPlanId` remis à `null` automatiquement
  (cascade côté fonction) plutôt que de rester avec une référence orpheline.
- **Catalogue de fonctionnalités illustratif, pas figé.** Le cahier des
  charges ne liste pas les feature flags exacts ("fonctionnalités
  activées" seulement) — `SubscriptionFeature` définit un petit
  ensemble rattaché à de vraies sections du projet (`bookings` → 5.8,
  `discounts` → 5.9, `prioritySupport`, `advancedReports`, `apiAccess`,
  `unlimitedGestionnaires`) plutôt que d'inventer des flags fictifs. Le
  backend n'valide pas cette liste (accepte n'importe quelle chaîne) —
  `SubscriptionPlanMapper` ignore silencieusement les valeurs inconnues.
- **Prix annuel toujours dérivé** (`monthlyPrice * 12 * 0.85`), jamais
  stocké séparément — les maquettes de référence montraient toujours
  exactement cette formule.
- **Aperçu d'impact avant suppression** : `listCompaniesByPlanId` (côté
  `CompanyRepository`, lecture simple) alimente la boîte de dialogue de
  confirmation, plutôt qu'une ressource de fonction dédiée à la
  "prévisualisation".

## Écrans réels
1. **`SubscriptionsListPage`** (Super Admin) — table/cartes responsive,
   bouton "Ajouter un Plan".
2. **`SubscriptionDetailPage`** — tarification (mensuel + annuel dérivé),
   fonctionnalités activées, actions Modifier/Supprimer.
3. **`ConfigureSubscriptionPage`** — formulaire unique création/édition
   (nom, description, prix mensuel, cases à cocher fonctionnalités).
4. **Boîte de dialogue de suppression** (`delete_plan_dialog.dart`) —
   liste des entreprises impactées + confirmation par saisie du nom du
   plan, correspondant aux maquettes de référence.

## Éléments volontairement omis
Hors cahier des charges 5.3, ou nécessitant une infrastructure au-delà de
CRUD+liste : cartes de statistiques (Plans Actifs/Total Clients/MRR/
Rétention), graphique "Analyse des Tendances", widget "Contacter un
consultant", barre d'usage "entreprises actives" par plan (nécessiterait
une requête d'agrégation par plan à chaque affichage de la liste),
dropdown "Cycle de Facturation" (le prix annuel est toujours dérivé, il
n'y a pas de choix de cycle à stocker), panneau "Entreprises" permanent
sur l'écran de détail (gardé uniquement dans la boîte de dialogue de
suppression, où il sert réellement la décision à prendre).

## Cas limites encore ouverts (non résolus par ce build, à clarifier avec la MOA si besoin)
- Une entreprise sans plan assigné (`subscriptionPlanId` null) : accès à
  quoi exactement ? Le contrôle d'accès réel aux fonctionnalités côté API
  ("contrôle d'accès côté API pour activer/désactiver des
  fonctionnalités", cahier des charges 5.3) n'est pas construit — ce
  build couvre le CRUD des plans eux-mêmes, pas encore l'application des
  feature flags dans les autres fonctionnalités.
