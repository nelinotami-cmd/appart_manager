# Feature 5.2 — Gestion des entreprises (SaaS)

## Statut d'implémentation
✅ **Implémenté sur les 3 couches.** Code : `lib/features/company/`
(entités incl. `contactName`, repository, 8 use cases, datasources Data,
`CompanyBloc`, 3 écrans - liste/détail/édition, responsives). Backend :
ressources `company.update-profile`, `company.update-status`,
`company.assign-subscription-plan` sur la fonction Appwrite unique `api`.
Lecture/liste/recherche/temps réel se font en accès direct client (pas de
fonction), grâce aux permissions par document
(`read(team:<companyId>)` + `read(label:superAdmin)`). Intégré au sidebar
`AppShell` ("Entreprises").

**Écrans réels (remplacent les descriptions "à concevoir" ci-dessous) :**
`CompaniesListPage` (Super Admin - table/cartes responsive, filtre par
statut), `CompanyDetailPage` (profil + bascule activer/désactiver pour
Super Admin), `EditCompanyPage` (formulaire profil pour tous ; statut +
plan d'abonnement visibles uniquement pour Super Admin, car restreints
côté backend).

**Éléments volontairement omis** (hors cahier des charges 5.2, ou
nécessitant une infrastructure au-delà de CRUD+liste) : upload de logo
(nécessiterait un bucket Storage complet), bouton "Inscrire une
Entreprise" séparé (création uniquement via 5.1), cartes de statistiques
(Total Clients/Taux d'Activation/MRR - MRR implique une facturation non
construite), journal d'audit, "Voir les factures".

**Décisions de scope prises pendant la construction :**
- Pas de ressource "créer une entreprise" séparée : la création reste
  exclusivement via l'inscription 5.1 (`auth.register-company-and-admin`)
  — une entreprise sans Admin/Team est un état que le cahier des charges
  ne décrit pas.
- Désactiver une entreprise désactive en cascade tous ses comptes
  (blocage de connexion immédiat), symétrique à la désactivation
  individuelle d'un Gestionnaire. Réactiver l'entreprise ne réactive PAS
  automatiquement ses comptes.
- Aucune UI (`CompanyBloc`, écrans) construite dans cette passe — le
  sidebar de navigation (`AppShell`) a une entrée "Entreprises" qui pointe
  vers un placeholder en attendant.

## Objectif métier
Donner à chaque entreprise cliente un profil administrable (nom, contact,
adresse), et au Super Admin la capacité d'activer/désactiver une
entreprise sur la plateforme. Pas de configuration multi-devise ni
multi-fuseau-horaire — tout est standardisé pour le Cameroun.

## Acteurs & permissions
| Acteur | Peut faire |
|---|---|
| Admin (entreprise) | Voir et modifier le profil de **sa propre** entreprise (nom, contact, adresse) |
| Super Admin | Voir/modifier le profil de **toute** entreprise, activer/désactiver une entreprise, lister toutes les entreprises de la plateforme |
| Gestionnaire | Aucun accès direct à ce module |

## Écrans à concevoir (aucun stub existant actuellement)
1. **Fiche entreprise (vue Admin)** — affichage + édition des champs
   nom/contact/adresse de sa propre entreprise. Pas de champ
   "changer le plan d'abonnement" ici (ça relève de 5.3, en lecture
   seule probablement pour l'Admin).
2. **Liste des entreprises (vue Super Admin)** — table avec recherche,
   statut actif/inactif visible en un coup d'œil, action rapide
   activer/désactiver.
3. **Détail entreprise (vue Super Admin)** — mêmes champs que la fiche
   Admin + statut + plan d'abonnement associé (lecture, lien vers 5.3
   pour modification du plan) + liste des utilisateurs de cette
   entreprise (lien vers l'écran 5.1 `CompanyUsersPage` filtré).
4. **Confirmation désactivation** — désactiver une entreprise bloque
   l'accès de tous ses utilisateurs ; une confirmation explicite doit le
   rappeler avant l'action.

## Modèle de données pertinent (`Company`, déjà défini dans le code)
| Champ | Type | Éditable par |
|---|---|---|
| name | texte | Admin (sa propre entreprise), Super Admin (toute entreprise) |
| contactEmail | email | Idem |
| contactPhone | téléphone | Idem |
| address | texte | Idem |
| status | active / inactive | Super Admin uniquement |
| subscriptionPlanId | référence (nullable) | Super Admin uniquement (voir 5.3) |

## Flux utilisateur clés (à construire)
1. **Admin modifie le profil de son entreprise** : formulaire pré-rempli
   → sauvegarde → confirmation inline, pas de rechargement de page.
2. **Super Admin désactive une entreprise** : liste → action rapide ou
   détail → confirmation → statut mis à jour immédiatement dans la
   liste ; tous les utilisateurs de cette entreprise perdent l'accès
   (à vérifier avec 5.1 : la désactivation entreprise devrait
   idéalement bloquer la connexion de tous ses comptes, pas seulement
   masquer l'entreprise — point à clarifier avec la MOA avant
   conception finale).
3. **Super Admin réactive une entreprise** : même écran, action inverse.

## États UI à prévoir
- **Chargement** : formulaire de fiche entreprise et liste Super Admin
  ont chacun leur propre état de chargement.
- **Vide** : liste Super Admin sans entreprise (cas rare mais possible
  en tout début de vie de la plateforme).
- **Erreur** : échec de sauvegarde du profil — conserver les valeurs
  saisies par l'utilisateur, ne pas les effacer sur erreur.
- **Lecture seule vs édition** : envisager un mode lecture par défaut sur
  la fiche entreprise avec un bouton "modifier" explicite plutôt qu'un
  formulaire toujours actif, pour réduire le risque de modification
  accidentelle.

## Cas limites
- Une entreprise désactivée doit-elle rester visible (grisée) dans les
  listes Super Admin, ou disparaître ? Recommandation : rester visible
  et filtrable par statut, ne jamais la cacher silencieusement.
- Que voit un Admin dont l'entreprise vient d'être désactivée pendant
  qu'il est connecté ? Prévoir un écran de blocage explicite plutôt
  qu'une erreur technique brute.

## Notes techniques utiles au design
- Comme pour 5.1, toute création/modification qui touche à des champs
  sensibles (statut, plan d'abonnement) devra probablement passer par
  une ressource dédiée sur la fonction Appwrite unique `api`
  (`company.update-status`, `company.assign-subscription-plan`, etc.),
  suivant la même convention de nommage que 5.1 — à construire au moment
  de l'implémentation, pas avant.
- Aucune notion de devise/fuseau horaire à prévoir dans les écrans —
  tout est implicitement "Cameroun".
